ЛАБОРАТОРНА РОБОТА №1

Тема / Патерн: Фабричний метод (Factory Method)
Завдання: Реалізувати гнучку підсистему каталогу товарів інтернет-магазину. Система повинна мати можливість динамічно створювати товари різних категорій («Електроніка», «Одяг») із власними специфічними атрибутами, не прив’язуючи клієнтський код до конкретних класів продукції.
Реалізація: Використано інтерфейс продукту IProduct, конкретні класи продуктів Electronics та Clothing, абстрактний клас творця ProductFactory та конкретні класи фабрик ElectronicsFactory і ClothingFactory.
Опис архітектури: Клієнтський код взаємодіє виключно з абстракціями. Замість прямого виклику оператора new, створення об'єктів делегується відповідній фабриці через перевизначений метод CreateProduct(). Це дозволяє масштабувати каталог і додавати нові типи товарів без зміни логіки головної програми.

ЛАБОРАТОРНА РОБОТА №2

Тема / Патерн: Одинак (Singleton)
Завдання: Створити централізований модуль збереження глобальних налаштувань інтернет-магазину (назва, робоча валюта), який повинен бути доступний з будь-якої точки програми, але існувати строго в одному екземплярі для запобігання розсинхронізації даних.
Реалізація: Використано клас налаштувань StoreSettings, приватний конструктор класу private StoreSettings(), статичний об'єкт для синхронізації потоків _lock та глобальну статичну точку доступу public static StoreSettings Instance.
Опис архітектури: Завдяки приватному конструктору унеможливлюється створення об'єкта ззовні через new. Доступ до єдиного екземпляра реалізовано через властивість Instance із впровадженням механізму потокобезпечного блокування (lock). Будь-які зміни атрибутів класу миттєво відображаються у всій системі.

ЛАБОРАТОРНА РОБОТА №3

Тема / Патерн: Адаптер (Adapter)
Завдання: Інтегрувати в систему внутрішніх платежів магазину сторонній закордонний сервіс (Stripe). Внутрішній інтерфейс програми працює виключно з гривнями (UAH), тоді як стороння бібліотека приймає лише долари (USD) та використовує зовсім іншу назву методів.
Реалізація: Використано внутрішній інтерфейс IPaymentProcessor з методом ProcessPayment, клас сторонньої системи ExternalStripeSystem з методами AuthorizeCard та ChargeDollars, а також клас-перехідник StripeAdapter.
Опис архітектури: Клас StripeAdapter реалізує наш стандартний інтерфейс IPaymentProcessor, але всередині себе агрегує об'єкт ExternalStripeSystem. При виклику методу оплати, адаптер самостійно конвертує UAH в USD за курсом та послідовно викликає специфічні методи стороннього сервісу.

ЛАБОРАТОРНА РОБОТА №4

Тема / Патерн: Декоратор (Decorator)
Завдання: Розробити систему гнучкого формування кінцевої вартості замовлення. Клієнт повинен мати можливість динамічно додавати до базового кошика товарів додаткові платні опції («Святкове пакування», «Експрес-доставка») у будь-яких комбінаціях.
Реалізація: Використано базовий інтерфейс замовлення IOrder, конкретний компонент StandardOrder (чиста вартість товарів), абстрактний базовий декоратор OrderDecorator, а також конкретні декоратори GiftWrappingDecorator та ExpressDeliveryDecorator.
Опис архітектури: Декоратори реалізують інтерфейс IOrder і водночас приймають об'єкт замовлення у свій конструктор. Це дозволяє динамічно нарощувати функціонал об'єкта «на льоту», огортаючи його новими шарами обов'язків та підсумовуючи фінальну вартість без модифікації початкових класів.

ЛАБОРАТОРНА РОБОТА №5

Тема / Патерн: Спостерігач (Observer)
Завдання: Реалізувати автоматизовану службу сповіщення користувачів та менеджменту складу про зміну статусу дефіцитного товару. Щойно товар з'являється в наявності, усі зацікавлені сторони мають миттєво отримати повідомлення.
Реалізація: Використано інтерфейс підписника ISubscriber з методом Update, конкретний клас спостерігача CustomerSubscriber (покупець) та клас суб'єкта (видавця) ProductStock, що містить динамічний список підписників List.
Опис архітектури: Об'єкти підписників реєструються в системі товару за допомогою методу Subscribe(). Коли відбувається зміна стану на складі через метод ChangeAvailability(), об'єкт по черзі обходить увесь список підписників та викликає їхній метод Update(), забезпечуючи слабку пов'язаність кодів.

ЛАБОРАТОРНА РОБОТА №6

Тема / Патерн: Стратегія (Strategy)
Завдання: Створити модуль розрахунку вартості доставки замовлення. Логіка калькуляції повинна кардинально змінюватися залежно від вибору клієнта («Самовивіз» — 0 грн, «Кур'єр» — 150 грн), без використання громіздких конструкцій if-else чи switch.
Реалізація: Використано інтерфейс алгоритмів IDeliveryStrategy, конкретні класи-стратегії SelfPickupStrategy та CourierDeliveryStrategy, а також клас контексту ShippingCalculator.
Опис архітектури: Замість жорстко прописаних розгалужень, клас ShippingCalculator делегує розрахунок об'єкту стратегії, посилання на який зберігається всередині. Завдяки методу SetStrategy() програма може миттєво підмінити один алгоритм іншим прямо під час виконання сесії.

ЛАБОРАТОРНА РОБОТА №7

Тема / Патерн: Фасад (Facade)
Завдання: Максимально спростити процес комплексного оформлення покупки (Checkout) для клієнтської частини програми. Сховати заплутану взаємодію окремих підсистем (перевірка й резервування товару на складі, списання коштів банком) за однією командою.
Реалізація: Використано класи ізольованих підсистем InventorySystem (Склад) та BillingSystem (Оплата), а також високорівневий інтерфейсний клас OrderProcessingFacade.
Опис архітектури: Клас OrderProcessingFacade слугує єдиним вікном доступу. Він інкапсулює всередині об'єкти складу та біллінгу. Клієнт робить один простий виклик методу PlaceOrder(), а фасад самостійно координує правильну та послідовну роботу всіх підсистем «під ключ».

ЛАБОРАТОРНА РОБОТА №8

Тема / Патерн: Стан (State)
Завдання: Реалізувати автоматичне відстеження та зміну поведінки замовлення залежно від його поточного етапу життєвого циклу («Нове» -> «Відправлено»). Система повинна динамічно блокувати неможливі операції (наприклад, скасування замовлення, яке вже відправлене клієнту).
Реалізація: Використано інтерфейс станів IOrderState із набором доступних дій, конкретні класи станів NewOrderState, PaidOrderState, ShippedOrderState та клас контексту замовлення OrderContext.
Опис архітектури: Об'єкт OrderContext володіє внутрішнім посиланням на поточний об'єкт стану. Замість умовних перевірок статусів через рядкові змінні, замовлення просто транслює запит клієнта поточному стану. Коли стан змінюється, об'єкт контексту підміняє внутрішній клас стану іншим, повністю змінюючи логіку своєї поведінки.
