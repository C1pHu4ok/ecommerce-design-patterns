Лабораторна робота №1: Патерн «Фабричний метод» (Factory Method)
Що реалізовано: Підсистему динамічного створення товарів різних категорій (Electronics, Clothing).

Обґрунтування: Використано інтерфейс IProduct та абстрактну фабрику ProductFactory. Конкретні фабрики самостійно вирішують, який об'єкт і з якими специфічними атрибутами (гарантія чи розмір) створювати. Це дозволяє масштабувати каталог товарів без модифікації існуючого клієнтського коду.

 Лабораторна робота №2: Патерн «Одинак» (Singleton)
Що реалізовано: Глобальний менеджер конфігурації платформи StoreSettings.

Обґрунтування: Конструктор класу зроблено приватним, а доступ реалізовано через статичну властивість Instance із застосуванням потокобезпечного блокування (Thread-safety lock). Це гарантує наявність лише одного об'єкта налаштувань у пам'яті програми та запобігає розсинхронізації даних (назви магазину, валюти тощо).

Лабораторна робота №3: Патерн «Адаптер» (Adapter)
Що реалізовано: Інтеграцію стороннього платіжного шлюзу ExternalStripeSystem.

Обґрунтування: Оскільки закордонна система Stripe приймає лише долари і має несумісні методи, було створено клас StripeAdapter, який реалізує наш внутрішній інтерфейс IPaymentProcessor. Адаптер бере на себе конвертацію валют та виклики сторонніх методів, роблячи процес прозорим для нашої платформи.

Лабораторна робота №4: Патерн «Декоратор» (Decorator)
Що реалізовано: Систему динамічного розрахунку вартості замовлення з додатковими послугами.

Обґрунтування: Замість створення безлічі підкласів, базове замовлення StandardOrder гнучко "огортається" декораторами GiftWrappingDecorator (святкове пакування) та ExpressDeliveryDecorator (швидка доставка). Це дозволяє комбінувати будь-яку кількість послуг «на льоту».

Лабораторна робота №5: Патерн «Спостерігач» (Observer)
Що реалізовано: Модуль автоматичних сповіщень про надходження дефіцитних товарів.

Обґрунтування: Об'єкт складу ProductStock виступає суб'єктом, що зберігає список підписників ISubscriber. При оновленні статусу товару через метод ChangeAvailability(), система автоматично розсилає повідомлення покупцям (CustomerSubscriber) без жорсткої прив'язки до їхніх конкретних класів.

Лабораторна робота №6: Патерн «Стратегія» (Strategy)
Що реалізовано: Гнучкий калькулятор вартості доставки.

Обґрунтування: Алгоритми розрахунку для різних типів логістики винесено в окремі класи (SelfPickupStrategy, CourierDeliveryStrategy). Клас ShippingCalculator виступає контекстом і дозволяє динамічно змінювати стратегію розрахунку прямо під час виконання програми, уникаючи громіздких конструкцій if-else.

Лабораторна робота №7: Патерн «Фасад» (Facade)
Що реалізовано: Спрощений інтерфейс для швидкого оформлення покупки (Checkout).

Обґрунтування: Складна взаємодія внутрішніх підсистем (резервування на складі, списання коштів більдінгом) прихована за високорівневим класом OrderProcessingFacade. Клієнт викликає один метод SimpleCheckout(), а фасад самостійно координує роботу підсистем.

Лабораторна робота №8: Патерн «Стан» (State)
Що реалізовано: Керування життєвим циклом та статусами замовлення.

Обґрунтування: Поведінку замовлення залежно від етапу (NewState, ShippedState) винесено в окремі класи, що реалізують інтерфейс IOrderState. Об'єкт замовлення делегує роботу поточному стану, що дозволяє автоматично змінювати логіку програми (наприклад, блокувати скасування замовлення, якщо товар уже відправлено кур'єром).
